The Challenge
You are building the Portola Ops Dashboard, the internal tool our operations team uses to monitor and manage stablecoin settlements. Work through each phase sequentially. Each phase introduces new requirements that build on your previous work.

Phase 1: The MVP
Estimated time: approximately 15 minutes
Build a functional settlement monitoring dashboard from scratch. This is your foundation. Prioritize getting something working on screen quickly.
Requirements
1.   Scaffold. Spin up a new React/Next.js app (or your preferred frontend stack).
2.   Mock Data. Generate 50 realistic transactions with the following fields:
•   ID (unique identifier)
•   Client Name
•   Amount (USD)
•   Status, one of: Pending, Cleared, or Failed
•   Timestamp

Data Tip: Make the data realistic. Include a mix of small amounts (under $1,000) and large institutional transfers (over $50,000) to create a representative dataset.

3.   The Grid. Display all 50 transactions in a clean, readable table.
4.   The Action. Add a Clear Funds button next to every Pending transaction.
•   Simulation: When clicked, call a mock API function that takes 1.5 seconds to resolve.
•   UX: The button must display Processing... and be disabled while the mock API is resolving.
•   Result: On success, the transaction status changes to Cleared and the button disappears.


Phase 2: Compliance
Estimated time: approximately 10 minutes
Compliance Update: New regulatory rules have been issued for large transfers. Implement the following changes to your existing dashboard.

Requirements
1.   High-Value Flag. Any transaction with an amount over $10,000 must be visually highlighted in red. The entire row should be clearly distinguishable from standard transactions.
2.   The Lock. The Clear Funds button must be disabled (locked) on all high-value transactions. Users should not be able to clear funds on transactions over $10,000 under normal operation.
3.   The Override. Implement a Super Admin toggle at the top of the page.
•   Default state: OFF. High-value transactions remain locked.
•   When toggled ON: The lock is removed and high-value transactions can be cleared normally.
•   This toggle should be clearly visible and its current state obvious to the user.


Phase 3: Live Fire
Estimated time: approximately 10 minutes
The system is now live. Transactions are streaming in real-time from the blockchain. Your dashboard must handle continuous incoming data without degrading usability.
Requirements
1.   The Feed. Set up a simulation that adds a new transaction to the top of the list every 2 seconds.
2.   The UX Challenge. Consider this scenario: you are about to click Clear on Row 3. A new transaction appears at the top, pushing all rows down. You accidentally click the wrong row.
3.   The Fix. Build a mechanism so the UI remains stable and usable even while data is actively streaming in.

Hint: How does Twitter/X handle new posts appearing in a live feed? What pattern do they use to prevent exactly this kind of disruption?


Phase 4: Batch Settlement
Estimated time: approximately 10 minutes
We have a backlog. Clicking through transactions one by one is too slow. Build batch processing capabilities with resilient error handling.
Requirements
1.   Selection. Add checkboxes to select multiple Pending transactions.
2.   Bulk Action. Add a Clear Selected button that processes all selected transactions.
3.   The Chaos. Modify your mock API so it has a 10% chance of failure (throwing an error) on any individual call.
4.   Optimistic Settlement. Implement resilient batch processing with the following behavior:
•   Run all selected transactions concurrently. Do not wait for one to finish before starting the next.
•   If 9 out of 10 succeed and 1 fails: the 9 should become Cleared and the 1 should revert to Pending (or show as Failed).
•   Each transaction result should be handled independently.

CONSTRAINT
Do NOT use Promise.all() for this batch operation. If one promise rejects inside Promise.all, the entire batch fails. You need each transaction to resolve or reject independently. Consider alternatives like Promise.allSettled() or handling each promise individually.
